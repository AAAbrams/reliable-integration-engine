# RIE Docs Sync

## Цель и границы

Поддерживай проектную документацию RIE достоверной, компактной и согласованной с кодом и принятыми решениями. Не превращай README в копию архитектурной спецификации. Не меняй архитектуру, чтобы замаскировать расхождение с реализацией.

Работай на русском языке. Имена классов, интерфейсов, API, CLI-команд, файлов, состояний и общепринятые технические термины сохраняй без перевода.

Соблюдай применимые `AGENTS.md` и прямые ограничения пользователя. Этот Skill не даёт самостоятельного разрешения редактировать файлы.

## Режим работы

- **Audit (по умолчанию):** только чтение и отчёт о необходимой актуализации документации. Не изменяй файлы.
- **Sync:** выполняй минимальные изменения только если пользователь явно разрешил редактировать конкретные документы или явно поручил их обновить. Не расширяй разрешённый набор файлов.
- Если разрешение на редактирование неоднозначно или противоречит применимым инструкциям, оставайся в Audit и покажи предлагаемый diff/план.

## Источники и ответственность

| Источник | За что отвечает |
| --- | --- |
| Фактический код, тесты, конфигурация, `composer.json` и инфраструктурные файлы | Что действительно реализовано, какие команды и зависимости реально существуют |
| `docs/RIE-MVP-architecture-v0.md` | Утверждённая базовая целевая архитектура MVP, инварианты и планируемые контракты |
| `docs/DECISIONS.md` | Явно принятые архитектурные решения и причины изменения baseline |
| `README.md` | Понятная точка входа, текущее состояние, возможности, запуск, проверки и ссылки |
| `AGENTS.md` | Постоянные правила разработки и работы агентов, а не эксплуатационная документация |

Не считай предложенную в спецификации возможность реализованной, пока она не подтверждена кодом. Не считай несовпадение кода и baseline разрешённым архитектурным решением. Если документы расходятся, обозначь конфликт и предложи решение человеку; не исправляй исходные решения молча.

## Workflow

### 1. Определить область изменений

1. Прочитай применимые `AGENTS.md`, `README.md`, `docs/RIE-MVP-architecture-v0.md` и `docs/DECISIONS.md` (если они существуют).
2. Определи предмет задачи, режим Audit/Sync и разрешённые файлы.
3. Изучи изменения через `git status --short`, `git diff --name-only`, `git diff --cached --name-only` и релевантные diff. Учитывай новые untracked-файлы. Если пользователь указал диапазон коммитов/PR, используй его вместо предположений о базовой ветке.
4. Изучи исходный код, тесты и конфигурацию, необходимые для проверки конкретных заявлений; не полагайся только на описание изменений от агента.

### 2. Классифицировать влияние

- **Новая реализованная функция / изменение API / статусов:** проверить `README.md` (текущее состояние, примеры только при наличии проверенных контрактов); оценить необходимость уточнения архитектурной спецификации.
- **Docker, PostgreSQL, CI, `.env.example`, Composer scripts, команды:** проверить инструкции запуска и тестирования в `README.md`; отделять существующее от будущего, а реально проверенное от непроверенного.
- **Изменение архитектурного инварианта, границы ответственности или гарантий:** указать отличие от baseline; предложить запись в `docs/DECISIONS.md` и изменение спецификации только после одобрения разработчиком.
- **Изменение правил работы агентов или процесса разработки:** рассмотреть `AGENTS.md`; не переносить внутренние правила в README.
- **Локальный рефакторинг без изменения публичного поведения или решений:** документация может не требовать правок; прямо сообщи об этом.

### 3. Отчёт Audit

Сообщи кратко:

1. Какие изменения изучены и как они подтверждены.
2. Какие документы требуют изменений и почему; какие не требуют.
3. Что является текущим фактом, что планом, а что не подтверждено.
4. Какие архитектурные расхождения требуют решения разработчика.
5. Конкретный список предлагаемых правок без изменения файлов.

### 4. Sync после разрешения

1. Меняй только разрешённые файлы и только затронутые разделы.
2. В README описывай фактические возможности. Не удаляй полезные предупреждения (например, о побочных эффектах `composer setup`).
3. Для архитектурных решений различай `proposed`, `approved` и `implemented`. Не меняй статус baseline без явного решения разработчика.
4. Не записывай ADR как принятое решение задним числом без подтверждения. При отсутствии согласования вынеси предложенный текст в отчёт, не добавляй его в журнал как утверждённый.
5. Используй относительные ссылки. Не добавляй несуществующие команды, endpoints, Docker-сервисы, CI-статусы, badges, лицензии или результаты тестов.
6. Не создавай дополнительные документы, каталоги и шаблоны без необходимости и разрешения.

### 5. Проверка

- Просмотри `git diff` и `git diff --check` для внесённых изменений.
- Проверь Markdown, относительные ссылки, имена файлов и соответствие упомянутых команд скриптам в репозитории.
- Сверь утверждения о готовности с кодом, конфигурацией и существующими тестами.
- Не запускай `composer setup`, миграции, установки зависимостей, сборку Docker, Git push/commit или другие операции с побочными эффектами без отдельного разрешения.
- Не заявляй об успешности проверок, которые не выполнялись. Если полноценная инструкция запуска ещё не проверена с чистого checkout, укажи это.

## Формат итогового ответа

- **Режим:** Audit или Sync.
- **Затронутые документы:** что изменено или предлагается изменить, с кратким основанием.
- **Проверки:** что действительно выполнено и результат.
- **Открытые вопросы:** противоречия, требующие решения человека; если нет — «Нет».
- **Границы:** какие файлы изменены; если режим Audit — «Файлы не изменялись».

## Примеры вызова

- `Используй $rie-docs-sync в режиме audit: оцени, что нужно обновить в документации после добавления Docker Compose и PostgreSQL.`
- `Используй $rie-docs-sync в режиме sync. Разрешаю изменить только README.md и docs/RIE-MVP-architecture-v0.md по согласованному плану. Не изменяй код.`
