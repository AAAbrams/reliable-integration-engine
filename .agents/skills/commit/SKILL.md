# Безопасное создание коммитов

Используй этот skill только тогда, когда пользователь явно просит создать Git-коммит (в том числе отдельными командами `коммит` или `commit`) либо прямо просит сгруппировать изменения и выполнить коммиты. Просьба **предложить сообщение коммита** без выполнения коммита **не** является разрешением на запуск `git commit`.

## Правила

- Явный запрос `коммит` / `commit` разрешает создавать локальные коммиты из безопасных изменений в **текущем репозитории**, принадлежность и назначение которых можно уверенно определить. Он не разрешает отправку изменений (`push`) или переписывание истории.
- Не определяй состав коммита только по текущему чату: изменения могли быть сделаны другими агентами, в других чатах или вручную. Прежде чем группировать изменения, изучи весь diff репозитория.
- В рамках этого skill никогда не выполняй `git add .`, `git add -A`, `git commit -a`, `git push`, `git reset`, `git restore`, `git clean`, `git stash`, `git rebase`, `git commit --amend` или `git commit --no-verify`. Не меняй конфигурацию Git или личность автора коммита.
- Не удаляй, не переписывай, не форматируй и не изменяй исходные файлы только ради создания коммита. Не добавляй в индекс игнорируемые файлы и секреты. Никогда не меняй уже подготовленный пользователем набор staged-изменений без явного разрешения.
- Если выполняется merge/rebase/cherry-pick, в индексе есть неразрешённые конфликты или невозможно однозначно определить репозиторий/worktree, остановись и объясни причину.
- Если окружение или доступные инструменты запрещают выполнение коммита, сообщи об ограничении; не утверждай, что коммит создан.

## 1. Изучи репозиторий

Сначала используй команды, не изменяющие состояние репозитория:

```sh
git rev-parse --show-toplevel
git branch --show-current
git status --short
git diff --stat
git diff --cached --stat
git diff --name-status
git diff --cached --name-status
git ls-files --others --exclude-standard
git log -5 --format=%s
```

Изучи фактические staged- и unstaged-изменения, а не только имена файлов. Прочитай содержимое важных новых текстовых файлов, не выводя секреты и не раскрывая слишком большие файлы целиком. Проверь, нет ли случайно добавленных учётных данных, файлов `.env`, приватных ключей, дампов, зависимостей, сгенерированных артефактов или персональных данных. Исключи такие файлы из коммитов, а если предполагаемую утечку невозможно безопасно устранить — остановись.

Отметь файлы, которые уже находились в индексе (staged) на момент запуска skill. Это может быть осознанный выбор пользователя. **Не удаляй их из индекса и не перераспределяй автоматически.** Если staged-изменения образуют один логически связанный коммит, их можно закоммитить в текущем виде. В противном случае остановись и запроси решение вместо изменения индекса.

Если изменений нет, сообщи об этом и заверши работу без коммита.

## 2. Спланируй логические коммиты

Выбери **минимальное разумное количество коммитов, каждый из которых можно понять отдельно**. Не создавай автоматически по одному коммиту на директорию, файл, инструмент, агента или тип Conventional Commits.

- Объединяй код, тесты, миграции и документацию, если они относятся к одному целостному изменению.
- Разделяй независимые функции, не связанные между собой исправления, инфраструктурные изменения, CI и документацию, если у каждой группы самостоятельная цель.
- Разделяй по агентам или чатам лишь тогда, когда происхождение изменений **достоверно известно** и группы логически самостоятельны. Принадлежность файла, Git diff и контекст текущего чата сами по себе не доказывают авторство изменений.
- Учитывай зависимости между группами: сначала базовая инфраструктура, затем изменения, зависящие от неё.
- Если один файл содержит изменения разного назначения, допускается выборочное добавление отдельных фрагментов (`git add -p`), **но только когда разделение безопасно и его можно проверить**. Иначе оставь согласованную группу вместе или запроси уточнение.
- Не считай, что все изменения рабочего дерева относятся к последней завершённой задаче.

Если планируется более одного коммита, кратко покажи предполагаемые группы, их названия и файлы до выполнения. Это информирование, **а не обязательный дополнительный запрос разрешения**, если состав изменений однозначен. При неоднозначных, посторонних, чувствительных или конфликтующих изменениях задай конкретный уточняющий вопрос вместо догадок.

## 3. Составь сообщения коммитов

Используй **Conventional Commits на английском языке**, если недавняя история репозитория явно не устанавливает другой стандарт:

`type(optional-scope): imperative summary`

Предпочтительные типы:

- `feat` — новая функциональность;
- `fix` — исправление ошибки;
- `refactor` — изменение структуры кода без намеренного изменения поведения;
- `test` — изменения только в тестах;
- `docs` — изменения только в документации;
- `build` — Docker, зависимости, окружение сборки;
- `ci` — автоматизация CI/CD;
- `chore` — прочее обслуживание проекта;
- `style` — изменения только в форматировании;
- `perf` — оптимизация производительности.

Первая строка должна быть краткой (обычно не более 72 символов), в повелительном наклонении и без точки в конце. Описывай **назначение изменения**, а не просто «обновление файлов». Добавляй тело сообщения, когда объяснение мотивации, компромиссов или особенностей миграции будет полезно при последующем просмотре истории. Не выдумывай номера задач, строки `Co-authored-by` или сведения об авторстве и происхождении изменений.

Примеры для RIE:

```text
build(docker): configure Laravel and PostgreSQL services
ci: add quality checks for PHP 8.4
chore(agents): add guided commit workflow
```

Это только примеры, а не заранее заданные сообщения: сначала изучи изменения.

## 4. Выборочно добавь изменения и проверь индекс

- Добавляй только явно выбранные пути командой `git add -- path1 path2 ...` или отдельные фрагменты через `git add -p -- path`. Никогда не добавляй весь репозиторий одной командой.
- Сохраняй уже подготовленные staged-изменения. Если добавление новых файлов смешает постороннюю работу с текущим индексом, остановись вместо изменения выбора пользователя.
- Перед **каждым** коммитом выполни:

```sh
git diff --cached --check
git diff --cached --stat
git diff --cached
```

- Сверь весь staged-патч с предполагаемой логической группой. Не коммить случайные изменения, сгенерированные файлы, секреты или посторонние staged-файлы.
- По возможности запусти наиболее подходящие существующие проверки проекта (тесты, линтеры, статический анализ), используя инструкции `AGENTS.md` и документированные команды. Не выдумывай успешные результаты. Различай проверки всего рабочего дерева и проверки именно того снимка изменений, который будет закоммичен.
- Если необходимые проверки не проходят из-за планируемого изменения, остановись и объясни проблему. Не обходи Git hooks.
- Если рабочее дерево неожиданно изменилось во время подготовки или создания коммита (в том числе из-за действий другого агента), проверь состояние заново и остановись, если есть риск захватить незавершённую чужую работу.

## 5. Создай коммиты и отчитайся

После проверки staged diff выполни `git commit -m "<message>"` (при необходимости добавь второй `-m` для поясняющего текста). Если логических групп несколько, повторяй анализ, подготовку индекса и проверки для каждой группы. Никогда не выполняй `push` автоматически.

После каждого успешного коммита проверь:

```sh
git show --stat --oneline --summary HEAD
git status --short
```

Итоговый отчёт на языке пользователя должен включать:

1. Короткий SHA и точный заголовок каждого созданного коммита.
2. Краткое объяснение логической группировки для каждого коммита.
3. Перечень реально запущенных проверок и их результаты.
4. Явный список оставшихся незакоммиченных изменений, если они есть.
5. Подтверждение, что `push` не выполнялся.

Если безопасно распределить изменения автоматически невозможно, не делай это принудительно: предложи разделение и объясни конкретное препятствие.
